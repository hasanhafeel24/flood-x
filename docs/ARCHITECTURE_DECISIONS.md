## ADR-001: Application Factory Pattern for FastAPI

**Status:** Accepted  
**Date:** 2026-09-01

### Context
Need a testable, configurable FastAPI application structure that supports multiple deployment modes (development, test, production).

### Decision
Use Application Factory pattern: `create_app()` in `main.py` returns a configured `FastAPI` instance with all middleware, routers, and lifecycle hooks.

### Consequences
- ✅ Easy unit testing (create fresh app per test)
- ✅ Settings injected via `core/config.py` — no global state
- ✅ Lifespan context manager handles startup/shutdown cleanly
- ⚠ Slight complexity vs direct app creation

## ADR-002: XGBoost for Flood Prediction (Not Deep Learning)

**Status:** Accepted  
**Date:** 2026-09-01

### Context
Need an ML model for flood classification and depth regression that is:
- Explainable to SIH judges and emergency managers
- Trainable in < 5 minutes on CPU
- Transparent about feature importance

### Options Considered
1. XGBoost (gradient boosted trees) ← **Selected**
2. LSTM / GRU (temporal deep learning)
3. Random Forest
4. Physics-only (SCS-CN)

### Decision
XGBoost Classifier + Regressor with StandardScaler preprocessing.

### Rationale
- Feature importances are directly interpretable (rainfall intensity: 34%, accumulated: 33%)
- Training time: 1.1 seconds on CPU (8000 samples)
- ROC-AUC: 0.998 — strong discrimination on synthetic data
- SHAP values available for additional explainability
- No GPU required for training or inference

### Limitations
- Trained on SYNTHETIC_PROTOTYPE data only
- Not validated on real Chennai flood events
- Performance on real observational data may differ significantly

### Real-Data Upgrade Path
Replace `services/ml/data_generator.py` samples with:
1. IMD historical rainfall (APHRODITE or AWS records)
2. Chennai Metrowater drainage sensor logs
3. Validated flood depth survey records (2015, 2021 Chennai floods)

## ADR-003: Synthetic Data First, Real Data Ready

**Status:** Accepted  
**Date:** 2026-09-01

### Context
No real-time Chennai sensor API access during prototype development. Need to demonstrate a credible end-to-end pipeline without fabricating real observations.

### Decision
All synthetic data is:
1. Explicitly labelled `SYNTHETIC_PROTOTYPE` in every API response
2. Declared in `DataProvenance` schema on every prediction
3. Physically grounded (SCS-CN hydrology, IMD thresholds, real Chennai coordinates)
4. Designed with defined real-data upgrade path

### What is Synthetic
- Rainfall intensity (generated by `providers/synthetic_rainfall.py`)
- Drainage utilization (generated by `providers/synthetic_drainage.py`)
- ML training data (generated by `services/ml/data_generator.py`)
- Road network (22-node approximation of Chennai road grid)

### What is Real
- Coordinate references (Chennai GPS coordinates from public maps)
- IMD rainfall classification thresholds (7.5/35.5/64.5/115.5 mm/hr)
- SCS-CN curve numbers (land use literature values)
- Road topology (approximate — verified against Chennai road maps)

## ADR-004: NetworkX for Road Routing (Not OSRM)

**Status:** Accepted  
**Date:** 2026-09-05

### Context
Flood-aware routing requires dynamic edge weight updates (flood depth changes in real time). Pre-computed routing engines (OSRM, Valhalla) do not support runtime weight modification.

### Decision
In-memory NetworkX DiGraph with Dijkstra's algorithm and custom flood weight function.

### Weight Function
```
weight = travel_min × risk_multiplier + depth_penalty
risk_multipliers: LOW=1.0, MODERATE=2.0, HIGH=5.0, CRITICAL=20.0
impassable: depth > 50cm → weight = ∞
```

### Real-Data Upgrade Path
Replace synthetic edge list with:
```python
import osmnx as ox
G = ox.graph_from_place("Chennai, India", network_type="drive")
```
Then add flood depth from sensor/model overlay.

## ADR-005: WebSocket for Real-Time Dashboard

**Status:** Accepted  
**Date:** 2026-09-01

### Context
Dashboard must display live simulation ticks (5-second interval). REST polling would add 5–10× request overhead.

### Decision
Single WebSocket endpoint `/ws` with JSON message protocol. Simulation engine broadcasts to all connected clients via `ws_manager.broadcast()`.

### Message Types
| Type | Direction | Payload |
|------|-----------|---------|
| `simulation_tick` | Server → Client | Full state snapshot |
| `simulation_reset` | Server → Client | Reset signal |
| `simulation:start` | Client → Server | Start command |
| `simulation:pause` | Client → Server | Pause/resume |

### Consequences
- ✅ Zero polling overhead
- ✅ All clients see same simulation state
- ⚠ Single WS endpoint — add `/ws/alerts` if alert bandwidth becomes large

## ADR-006: Decision Support, Not Autonomous Actions

**Status:** Mandatory  
**Date:** 2026-09-01

### Context
AI system generates flood response recommendations. There is a risk of system autonomously dispatching orders or creating a false sense of authority.

### Decision
All decision engine outputs:
1. Include explicit `disclaimer` field: "Decision-support only — not official emergency orders"
2. Require `confidence` score (0–1) with all recommendations
3. Show `triggered_by` condition for full transparency
4. Are ranked by urgency but require human authorisation before action

### Implementation
- `services/decisions/engine.py` — every `Recommendation` has `disclaimer` field
- API response includes package-level disclaimer
- UI labels every recommendations tab with "DECISION SUPPORT ONLY — NOT OFFICIAL"

## ADR-007: Graceful Database Fallback

**Status:** Accepted  
**Date:** 2026-09-05

### Context
Backend must be demonstrable without a running PostgreSQL instance (e.g., at SIH venue on laptop).

### Decision
Database initialization is wrapped in `try/except` in the lifespan handler. If PostgreSQL is unavailable, backend falls back to `SYNTHETIC_SIMULATION` mode — all simulation, prediction, and routing features work without persistence.

### Consequence
- ✅ Demo works without Docker or database
- ⚠ No historical query persistence in fallback mode
- Production deployment should always use PostgreSQL + Alembic migrations
